Freeze, restore and use releases

What a frozen version means

A frozen release preserves a verified set of dataset files and saved metadata under arc/. Continuing work or restoring an older draft does not overwrite that release. Use Dataset lifecycle → Frozen releases.

The current controls implement local freezing, restoration, checkpoints and recovery. They do not upload or withdraw remote files, maintain a remote published-current pointer or provide a QGIS plugin. The edition controls can record publication and withdrawal locally. Flow catalogue publication is a separate workflow.

Keep in-house and public editions

Use Dataset lifecycle → In-house and public editions when the internal and public products have different files, attributes or documentation. Each edition is a separate dataset record with its own UUID, working folder, metadata, citation and version history. A shared family identifier groups them. A public edition records the exact in-house release UUID, source version and ZIP checksum used to prepare it.

Freezing an in-house edition creates a stable operational baseline without publishing it. The public edition can have a different version number and release schedule: for example, public 1.4.0 may derive from in-house 2.3.0. Later internal edits never change either frozen ZIP.

Freeze the in-house baseline

  1. Select the internal dataset and open Dataset lifecycle → In-house and public editions.
  2. Choose Designate this draft as in-house. This requires an unlocked working draft. Existing frozen releases remain unchanged; an older release of this designated dataset can still be selected as a source.
  3. Complete the internal metadata and documentation. Designating an edition changes saved metadata, so obtain fresh approval and prepare the PDF again before the next freeze.
  4. Use Frozen releases to preview and freeze the version, keeping or closing the working copy as needed.

Make a public edition

Select the Frozen in-house source, then choose Make public edition. The three-step workflow replaces copying folders and rebuilding a metadata template:

  1. Choose public content. Common data files are suggested automatically. Supporting documents remain opt-in. CSV/TSV columns and GeoPackage/GeoJSON layers and attributes can be selected directly. Untick unwanted layers or remove attributes; geometry is retained. Other formats copy intact, so include companion files and inspect their contents. Prepared metadata documents, hidden application files and archive/database transport files are excluded from the source selection.
  2. Review public documentation. The public title, abstract, purpose, keywords, authors, owners, citation dates, topic categories and coverage are prefilled from the frozen source. Definitions, aliases and units follow retained attributes only. Edit the public wording and version; inspect All prefilled metadata and field definitions. Rights, licence restrictions, use limitations and embargo information are inherited and need review. Copying metadata does not grant permission to distribute.
  3. Prepare public draft. Review the summary of included/excluded files and attributes, inherited metadata and remaining review items. Choose Create and open public draft. Datapond creates a separate UUID and folder in dev/, scans the files, registers the retained attributes, extracts supported spatial extents, generates a citation for the public title/version, and opens the new dataset for editing.

The in-house dataset and frozen ZIP stay unchanged. Review temporal coverage and the geographic description against the actual public selection; dates and place names cannot always be inferred from the files. Geometry simplification and row filtering are performed in your GIS or processing tools, then checked in the public draft. Maintain scripts and lineage for those transformations.

Complete the public metadata and documentation, obtain fresh approval, prepare and inspect the public PDF and complete folder, then freeze the public version. Internal review records, approval, internal lineage narratives, licence notes and development history are not copied by the metadata defaults. A development document is copied only if you select that file explicitly.

Set reusable metadata and contact defaults

Before freezing the in-house source, choose Public metadata defaults. Mark descriptive fields or groups that contain internal wording and should be omitted from future public drafts. The policy is captured with the frozen source, so changing the working policy does not change an older release. Rights and restrictions cannot be excluded using these defaults.

You can also nominate a public contact for an organisation. New public editions use their first owner organisation and its nominated person. Without a nominated person, they use the organisation contact itself; they do not copy the in-house dataset’s individual points of contact. If there is no owner organisation, add the appropriate public contact in the new draft. Organisation contact defaults apply to future creation; an update preserves existing public contacts.

Update the same public edition from a newer source

  1. Select the existing public dataset and its newer Frozen in-house source, then choose Update this public edition. If its working copy was closed, restore a public release as a draft first.
  2. Previous file, layer and attribute choices are selected again. New files and attributes are listed for review and are not added to the saved selection automatically. Removed source items are highlighted. Adjust the selection where needed.
  3. Review the comparison between the previous source metadata, current public metadata and new source. Unchanged source values keep the public wording. Source changes are adopted when the public value still matches the old source. When both versions changed differently, choose Current public or New source. For descriptive text, you can then refine the wording in the form.
  4. Existing public supporting documents and contacts are retained. If a managed data file was edited in the public draft and the source replacement also changed, choose whether to keep the public file or use the new selected source content. This also protects local simplifications and row filtering from silent replacement; keeping such a file does not apply newer source observations to it.
  5. Review the summary and create the updated draft. It keeps the public UUID, uses the chosen public version, records the new exact source and adds a lineage step. A recovery checkpoint preserves the complete previous public metadata and working folder. Under Frozen releases, select the checkpoint and restore it to undo an update—even if this public edition has never been frozen.

The updated draft is scanned again. Attribute descriptions survive for retained fields; automatic spatial extents are recalculated. Refresh file-specific quality assessments and manually entered file extents, which belong to the earlier data. Review coverage, rights, citation and documentation, obtain fresh approval, prepare the PDF and freeze the new public version. Earlier releases and the currently published pointer stay unchanged.

The comparison baseline is private to the creating pond. Local frozen snapshots and recovery checkpoints preserve it. Public transport packages omit it, so an imported public dataset can be edited and linked manually but cannot use the automated update workflow without a locally created comparison baseline.

Link an already prepared public dataset

Select that dataset, choose the exact Frozen in-house source, describe the preparation method and choose Link this existing public draft to source. This records provenance for files you have already prepared. It does not generate files or a metadata comparison baseline. The public record must have a different UUID from its source. Manually changing a source link clears any saved comparison baseline; use the guided update for editions created with this workflow.

An edition cannot be switched between in-house and public, and an existing public edition cannot move to a different family. Restoring a public release restores the source link and method captured with that version. If a snapshot predates edition designation, the edition identity is retained; for a public edition its source link is cleared, so link the correct source before reviewing and freezing again. Portable transfer preserves family and source UUIDs even when the source dataset is absent from the receiving pond.

Track which public version was distributed

Distribute the reviewed public package through your usual authorised publishing process. Then select its Frozen public release, record the Publication location or URL and note, and choose Record as currently published. This records distribution already carried out; it does not upload files or grant distribution permission.

Pond overview also labels editions and their published version. The family table shows each edition’s Latest frozen version, the Currently published version, and the working public edition’s In-house source version independently. Freezing a newer public version does not change the published pointer. Recording a replacement updates that pointer and retains the publication history. After withdrawing the current release externally, choose Record withdrawal. This does not remove remote copies. The currently published ZIP is protected from stale-release removal until a replacement or withdrawal is recorded.

Publication records are local to the pond and are not transferred or rolled back when a draft is restored. The public frozen metadata and portable transfer database omit local review/import history, application accounts, internal-field policies and private comparison baselines; the private restoration snapshot retains them. Explicit public author/contact records and selected supporting documents still accompany the public package, so inspect them before distribution.

If public-draft creation is interrupted, select the in-house source dataset and use Recover interrupted lifecycle operation. A committed public record is retained; an unregistered draft is preserved privately for inspection. For an interrupted update, select the public dataset and use the same recovery control. Backups should include .metadata_pond/edition-drafts/ and .metadata_pond/releases/operations/ with the rest of .metadata_pond/.

Prepare the dataset for freezing

Save a meaningful version in major.minor.patch form (for example 1.0.0) and a citation. Finish or cancel an active metadata review. Under Dataset status → Human-readable metadata, choose Save PDF to dataset folder. Open metadata.pdf from the dataset folder, or first select Also download the PDF for preview for a browser copy. Inspect the complete dataset folder and check what an external recipient will receive.

Before preparing that PDF, select Essential or Full in Configuration and complete all required sections in Dataset status for that mode. A reviewer must save the latest metadata review with status Approved. Approval applies to the saved metadata: later changes require fresh approval. Older approvals without a saved approval snapshot also need a new review before a new freeze. Preparing a PDF or ticking the folder-review confirmation does not replace metadata approval.

Before freezing a version

These personal ticks do not replace the confirmation or validation in the app. Freezing includes every file under the dataset root, including hidden files and old transport ZIPs. Remove unwanted material deliberately before previewing; the app does not guess what to exclude. Leave enough free space for staging, the archive and any preserved draft.

Freeze and verify

  1. Choose Preview saved dataset. Review the displayed Essential or Full assessment, reviewer, file list and checks. Incomplete metadata, missing or stale approval, unsafe paths, symbolic links, case-colliding names or stale/changed prepared documents stop the operation. Switching assessment modes clears the preview.
  2. Confirm in the app that you opened the PDF and reviewed the previewed folder, and enter release notes.
  3. Choose Freeze version; keep working copy to continue developing, or Freeze version and close development to retire the working folder after verification.
  4. Select the new release and verify it. A frozen version cannot be overwritten; save a different version before making the next release.

Choose an ISO validation policy only when that release requires an ISO package. A requested ISO export failure stops the freeze. For an already frozen matching draft, Close development using selected release avoids making another release and checks that its metadata and files still match.

Both freeze choices recheck completeness and approval. The release manifest records the assessment mode and reviewer. Pond overview identifies frozen versions without reporting metadata completeness; a retained working copy stays identified as frozen while its saved metadata matches. Later edits are development work and do not change the frozen release. Existing frozen releases remain intact.

Distribute the release

arc/releases/<release-id>/
  dataset.zip
  release.json
  files.json
  checksums.sha256

Keep the three sidecars with the ZIP when distributing outside DataPond. The app’s ZIP download currently downloads the ZIP alone; collect the sidecars from the release folder as well.

The ZIP preserves the dataset in dataset/, plus a portable dataset metadata database, metadata.pdf, its QMD source and portable theme, citation.txt, README.txt and a licence summary. The metadata database includes referenced contacts. In-house and unclassified editions also include review history; public editions omit local review/import history and application accounts. Root QMD/Rmd development documents are acknowledged and preserved without execution. Read the recorded rights before sending the files: a successful freeze is not a distribution approval.

To import a new frozen release into another pond, select its dataset.zip under Portable dataset transfer → Import dataset in the receiving pond. The dataset UUID, version, files and metadata are retained, with paths and linked records adapted to that pond. The release UUID is recorded as the import bundle ID. An existing dataset with the same UUID will not be overwritten. This creates a working dataset record; the original pond’s release history stays there.

Private metadata snapshots remain inside .metadata_pond/ for restoring releases in the original pond. Back them up with the catalogue and archive. Earlier frozen ZIPs without a transfer database still use that original restore workflow. Checksums detect changed files but do not prevent someone modifying them outside the app.

Restore an older release or roll back a draft

Restore selected release as draft restores its saved files and metadata into a new dev/ folder. The dataset UUID and catalogue ID stay the same, and the frozen release remains unchanged. If a working draft exists, the app first preserves it as a verified private checkpoint.

Roll back to selected working-draft checkpoint restores that prior draft and checkpoints the draft it replaces. Check the restored state, make your changes, then save a new version before freezing again. Releases and checkpoints do not expire automatically in this version.

Restoration can stop when shared people, organisation, licence or vocabulary references have changed. Resolve the reported differences with the curator; do not overwrite shared definitions merely to force the restore.

Remove stale release ZIPs

To reclaim space, a pond administrator can select an older release in Release history, enter a reason in Release notes / reason for the operation, and choose Remove selected stale release ZIP…. The preview shows the version being removed, the space it occupies and the version that will remain. Read the preview, tick the permanent-removal confirmation, then choose Permanently remove this ZIP.

This removes the ZIP and keeps its metadata, checksums and history. The history row shows removed; that version can no longer be downloaded or restored from this pond, and its version number cannot be reused. The newest frozen release is protected. A release backing the current archived dataset, or needed by a working-draft recovery checkpoint, is also protected. Checkpoints and other releases are not deleted automatically.

Removal affects local storage. If you upload with rclone copy, the SharePoint copy stays there. A suitably scoped rclone sync can propagate the deletion; inspect its --dry-run first. SharePoint retention or recycle-bin policies may delay storage reclamation. Existing consumer caches are independent copies.

If removal is interrupted, the row may show removing. Use Recover interrupted lifecycle operation as a pond administrator to finish it before another lifecycle action. The operation keeps an audit record of who removed the ZIP, when and why.

Recover an interrupted operation

Use Recover interrupted lifecycle operation after an interruption. The app checks its operation journal and preserved files before completing or reconciling the operation. It refuses to interrupt a live process or a lock from another computer. Do not delete locks or staging folders to bypass a refusal; retain the error and ask the maintainer to inspect it.

Use one extracted consumer cache

The current R helper can cache a release from a local pond. It stages the ZIP, verifies it, extracts and verifies the files, then exposes a stable folder named for that release. The transport ZIP is removed by default; keep_zip = TRUE deliberately retains it.

# Replace these values with an existing local pond, release ID and cache folder.
pond <- "/path/to/pond"
release_id <- "existing-release-id"
cache_root <- "/path/to/consumer-cache"
cached <- datapond::cache_dataset_release(release_id, pond, cache = cache_root)
datapond::verify_cached_dataset_release(cached)
file.path(cached, "release", "dataset", "data")

Open the required files under that last path in QGIS manually. Treat cached files as read-only, and copy them to a working dataset before editing. Keeping each release at its own path lets a project refer to a particular version. Remote Flow downloads, automatic cache eviction/project pinning and the QGIS plugin are future work.
